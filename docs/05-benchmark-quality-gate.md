## 客户侧借鉴重点

客户侧的核心不是“仓库介绍”，而是让中国跨境卖家相信：英国仓的入库、库存、履约、退货、FBA、账单都可视、可追责、可对账。

必须体现：

- 多平台支持：Amazon UK、eBay UK、TikTok Shop、Shopify、Temu、B2B 出货。
- 服务场景化：发货到英国仓 -> 上架可售 -> 平台订单履约 -> 退货质检换标 -> FBA 补仓 -> 账单对账。
- 费用透明：费用明细、计费事件、账单状态、来源单据跳转。
- 轨迹可视：ASN 到仓状态、订单状态、退货状态、异常工单状态和照片凭证。
- 中文协同：异常中心、工单中心、资料补交、客户确认闭环。
- 合规资料：VAT、EORI、FHDDS、授权资料、进口文件留档。

## 仓库后台借鉴重点

仓库后台应向 WMS 学，而不是向普通 ERP 表格学。

必须体现：

- 扫码优先：收货、上架、拣货、复核、出库、退货质检都默认支持条码/箱唛/库位扫描。
- 任务队列：待收货、待上架、待拣货、待复核、面单失败、地址异常、退货待质检、库存调整待审核。
- 库位模型：receiving、storage、picking、returns、fba、exception、packing、dispatch 等区域。
- 波次策略：按平台、渠道、截单时间、承运商、SKU 热度生成拣货波次。
- 出库强控制：packing scan、称重、尺寸、面单、跟踪号、交接批次、出库扫描。
- 异常标准化：异常关联 ASN、订单、SKU、库位、照片、责任方、处理 SLA、客户确认记录。
- 仓内 KPI：到仓未收、收货差异、上架及时率、拣货准确率、按时出库率、退货处理时长、异常未关闭数量、库位利用率。

## 技术与数据模型借鉴重点

必须遵守：

- 库存不能只存余额，要有 `InventoryLedger` 流水账。
- `InventoryBalance` 只是可重建快照。
- 库存口径必须统一：`available = on_hand - reserved - frozen/quarantine - threshold`。
- 库位是层级树，不是文本字段：warehouse -> zone -> aisle -> rack -> shelf/bin。
- 订单锁库与出库扣库分离：reservation、pick、pack、ship_confirm。
- 每一笔费用来自 `ChargeEvent`，人工调整也必须有原因和审批。
- 承运商接口通过 `CarrierAdapter` / `ShippingProvider` 抽象，不写死 Royal Mail、DPD、Evri、Yodel。
- 开源项目只借鉴模型，不直接照搬业务。

## 当前网站原型缺口

第一阶段网站原型已覆盖官网首页、客户工作台、仓库后台、数据蓝图和开发路线，但仍需补齐：

- 官网信息架构：服务项目、平台方案、合规中心、价格说明、帮助中心、联系我们。
- 价格/计费说明：仓储费、操作费、尾程费、退货费、FBA prep、最低消费、增值服务。
- 真实转化动作：提交询盘、上传 SKU 模板、获取报价、预约仓库方案、创建入库预报 Demo、联系客服。
- 客户门户流程：创建 ASN、导入订单、确认退货处理方式。
- 仓库后台细节：收货扫描、差异登记、上架分配、拣货复核、称重出库、退货拍照质检。
- 集成边界说明：第一阶段支持手工/CSV；第二阶段支持 Shopify/API；后续支持平台和承运商接口。
- 信任证据：仓库地址/覆盖区域、SLA、服务流程、照片或示意资产、常见问题、合规说明、数据安全说明、联系方式。
- 移动端仓内作业：至少展示一个 PDA/手机扫码任务流。
- 移动端客户操作：客户应能在手机浏览器里完成查库存、看订单、看异常、确认退货处理、补交入库资料、查看账单等高频动作。

## 移动端设计原则

移动端不是桌面端的缩小版。客户在移动端的使用场景通常是微信沟通中临时查看、确认、补资料和转发，不适合复杂表格和大批量管理。

必须优先支持：

- 快速查看：库存摘要、订单状态、入库状态、异常数量、账单待确认。
- 快速确认：入库差异确认、退货处理方式确认、异常处理方案确认。
- 快速补资料：VAT/EORI/FHDDS 授权、装箱单、箱唛、SKU 图片、退货照片。
- 快速联系：一键进入工单/客服、复制单号、查看处理记录。
- 快速支付/对账：查看费用来源、下载账单、上传付款凭证。

移动端界面要求：

- 首页首屏不能横向滚动，正文宽度必须等于视口宽度。
- 关键按钮高度不低于 44px，适合手指点击。
- 表格在移动端必须转为卡片、摘要列表或局部横向滚动，不能撑破页面。
- 状态标签要足够清楚，优先显示“待我处理”的任务。
- 每个移动端流程最多 3-5 步完成，避免长表单。
- 上传资料必须支持手机相册/拍照。
- 错误提示必须具体到字段和处理方式。
- 移动端不承担复杂仓库管理，但要支持客户确认和仓内扫码任务的轻量演示。

## P0 质量门禁

- 中文、英文、符号、英镑金额在源码、浏览器、移动端均无乱码。
- 移动端 390px 宽度下无页面级横向滚动。
- 每个客户数据都带 `customer_id` / `tenant_id`，客户之间不可越权访问。
- SKU、ASN、库存、订单、退货、FBA、账单都有唯一编号和状态机。
- 所有库存变化必须写入 `InventoryLedger`。
- `InventoryBalance` 可从 ledger 重算并与当前余额一致。
- 订单创建只锁库，不直接扣实物库存；出库确认后才扣减。
- 每一笔费用必须来自 `ChargeEvent`，并能追溯到来源单据。
- 异常必须有关联对象、责任方、状态、处理记录、关闭结果。
- 重要操作有 audit log：创建、修改、审核、锁库、扣库、计费、作废。
- CSV/Excel 导入有字段校验、错误行提示、幂等处理和重复单号防护。

## P1 质量门禁

- 客户可完成：注册/KYC -> SKU -> ASN -> 查看入库差异 -> 查看库存流水。
- 客户可在移动端完成：查看库存摘要、查看订单状态、确认异常、确认退货处理方式、补交入库资料。
- 仓库可完成：收货 -> 差异 -> 上架 -> 库存转可售。
- 客户可完成：订单导入 -> 库存锁定 -> 查看履约状态 -> 查看跟踪号。
- 仓库可完成：拣货 -> 复核 -> 称重 -> 面单/运单号 -> 出库确认。
- 退货可完成：到仓登记 -> 质检拍照 -> 客户确认 -> 重上架/换标/销毁。
- FBA 可完成：创建补仓单 -> 锁库 -> 贴标/换箱/打托 -> 出库。
- 财务可生成账单，客户可查看费用来源和下载账单。
- 客服可在异常中心处理客户确认和资料补交。

## P2 质量门禁

- Shopify、Amazon/eBay/TikTok 等平台订单接入前，先完成统一订单接口模型。
- 承运商接口通过 adapter 层接入，不污染订单核心模型。
- 面单失败、地址异常、库存不足能自动进入异常中心。
- 支持多仓、多库区、多库位、多币种、多时区。
- 支持仓内移动/PDA 扫描。
- 支持库存盘点、库存调整审批、低库存提醒。
- 支持 webhook/API 回传订单状态、库存状态、跟踪号。

## 质量红线

- 库存不能靠直接改余额解决。
- 费用不能靠手写账单行解决。
- 异常不能只靠备注字段解决。
- 客户隔离不能只靠前端过滤解决。
- 状态流转不能只靠自由文本解决。
- 平台/物流集成不能写成一次性硬编码。

## 一句话标准

第一阶段原型要让客户相信“这不是展示页，而是未来系统的可信雏形”；后续开发要让仓库、客服、财务和客户围绕同一套单据、库存流水、异常记录和费用事件协作。
