# Community Feedback Request Guide

Use this guide when asking friends, early users, or contributors to look at Open Warehouse System during the Codex for OSS application period.

The goal is not only to collect stars or forks. The more useful goal is to collect real signals: who understands the project, which workflow they tried, what confused them, what issue they can reproduce, and what small contribution they may want to make.

## Repository Link

Share this public repository URL:

```text
https://github.com/BarneyD66/open-warehouse-system
```

## Healthy Ask

Ask for one of these actions:

- Star the repository if the project direction is useful.
- Fork the repository if they want to inspect, run, adapt, or contribute.
- Open a GitHub issue with a reproducible setup problem, workflow question, or documentation gap.
- Try the README quick start and report where onboarding is unclear.
- Review one customer-facing workflow for localization or regional assumptions.

Avoid asking people to create empty forks, low-quality issues, or fake activity. Reviewers can usually distinguish durable OSS interest from noisy activity.

## Copy-ready Short Message

```text
I am preparing Open Warehouse System for the Codex for OSS program. It is a Chinese-first, global-ready WMS starter for cross-border warehouse, fulfillment, inventory, returns, billing, and 3PL workflows.

If the project is relevant to you, a star helps. If you want to inspect or adapt it, a fork or small issue with feedback helps even more:
https://github.com/BarneyD66/open-warehouse-system
```

## Useful Feedback Questions

When someone reviews the project, ask:

- Could you understand the project purpose from `README.en.md`?
- Did the quick start make sense?
- Which workflow did you review: customer, ops, warehouse, billing, inventory, returns, or tracking?
- Did anything look unsafe, unclear, or over-claimed?
- Which part would make a good first issue?
- If you work in another region, what language, carrier, address, tax, customs, privacy, or billing assumptions would need adaptation?

## Public Data Safety

Feedback, screenshots, issues, and pull requests must not include:

- Real customer names, addresses, phone numbers, emails, labels, or tracking numbers.
- Production URLs, database URLs, `.env.local`, secrets, credentials, provider dashboards, or logs.
- Payment proofs, private pricing sheets, invoices, warehouse documents, or customer uploads.

Use fake demo data only.

## Maintainer Follow-up

After receiving feedback:

1. Convert specific setup or workflow problems into GitHub issues.
2. Add `good first issue` only when the task is small, reproducible, and safe for a first contributor.
3. Link relevant docs such as `docs/OSS_REVIEWER_FAQ.md`, `docs/CONTRIBUTOR_QUICK_PATH.md`, `docs/GLOBAL_READINESS_REVIEW.md`, or `docs/SMOKE_TEST_PLAN.md`.
4. Keep private customer, carrier, pricing, and production details out of public follow-up.
